#+title: The term data structure
#+author: libpeg

The value representation PEG rules produce: one tagged node type serving
all three value-producing arrow modes, its spans, its reference counting,
its printer, and the invariants a checker can enforce.  This is the
normative specification of =src/term/= (L3 of the layer stack) and of the
capture payload frozen as item 3 of the interface freeze (PLAN.org §5.1).

* Scope and status
:PROPERTIES:
:ID:       term-scope
:END:

This document expands PLAN.org D9 into a full specification.  It is
consistent with D2 (arrow dash count is value richness), D8 (the target
floor is Cortex-M/ESP32 with ≥64 KB RAM), D10 (=pegvm= is the consumer of
this printer), §5.2 (the term type), R6 (the two-counters hazard), S5
(traversal recurses to input depth), S7 (the capture payload cannot carry
a value today) and S8 (positions are =int= across every layer — they must
not be here).

It is *not* the specification of the grammar surface (that is
=docs/grammar.org=) or of the =pegvm= wire protocol (that is
=docs/protocol.org=).

** How to read the requirements in this document

Three kinds of statement appear below, and they are not interchangeable:

- *Requirements* — fixed by PLAN.org or forced by a constraint recorded
  there.  An implementation that does otherwise is wrong.
- *Decisions* — points PLAN.org leaves unnamed but that must be pinned
  before code can be written (a spelling, a return convention).  Marked
  *this document's decision*; they are revisitable, and the reason is
  given so that they can be.
- *=Implementer's discretion.== — a genuinely free choice.  It must be
  recorded in the module header, because a caller that cannot see the
  header cannot see the choice.  The free choices are collected in §8.

* The node
:PROPERTIES:
:ID:       term-node
:END:

One structure serves all three arrow modes (D9).  There is no separate
text node type, no separate tree type, and one traversal and one printer.

#+begin_c
struct peg_node {
	peg_tag   tag;          /* the "tagged" part: the name the grammar
	                           wrote; NULL for a text node            */
	struct peg_node *prev;  /* weak back-link within the sibling chain */
	struct peg_node *next;  /* owned: this node holds a reference to
	                           its successor                         */
	struct peg_node *sub;   /* owned: head of the child list, or NULL  */
	peg_span  span;         /* byte range — this is the memo key       */
	uint32_t  ref;          /* this node's owners (see §4)             */
};
#+end_c

=ref= is not in D9's sketch; PLAN.org §5.2 requires it ("Refcount on the
node") and §5.1 lists =peg_node= as freeze item 3, so it belongs in
the struct that is frozen.  =prev= is in D9's sketch and is the field an
implementer is most likely to "simplify away".  Do not: §2.2 explains what
it buys.

** Field by field
:PROPERTIES:
:ID:       term-fields
:END:

| field  | what it is for |
|--------+----------------|
| =tag=  | The node's identity: the name the grammar wrote for it.  It is what the printer emits as the s-expression head, and — with =span.lo= — the part of the memo key a node can recover by itself.  =NULL= marks a *text node*, whose value is the subject bytes over its span. |
| =prev= | The back-link of the sibling chain.  *Weak*: it is never counted and never dereferenced during destruction (§4, §5).  It exists so that splicing a node, or a whole chain, into another position is O(1). |
| =next= | The forward link of the sibling chain.  *Owned*: a node holds one reference to its successor (§4.1). |
| =sub=  | The child list of a structured node: the head node of a chain, which this node owns.  =NULL= for a text node and for a structured node whose value list is empty. |
| =span= | Two positions, half-open: the bytes of the subject this node's value covers (§3).  It is the memo key in the sense that =(tag, span.lo)= identifies the rule application the node came from. |
| =ref=  | How many owners hold this node (§4).  Reaching zero destroys the node and everything it owns. |

*Requirements on the fields.*

- =span= holds two =peg_pos= values, one typedef for every position and
  length in the API (freeze item 1).  It is *not* =int=: S8 records that
  =int= positions cap the subject at 32 KB on a 16-bit-=int= target.
- =tag= spells a name in the identifier lexical class
  (=[A-Za-z_][A-Za-z0-9_]*=), because the printer emits it unquoted as an
  s-expression head and the reader must read it back as an atom (§6).
- =tag != NULL= ⟺ the node is a structured node.  A text node has
  =tag == NULL= and =sub == NULL= always.

*=Implementer's discretion.=* The concrete type behind =peg_tag= (an
interned atom, an index into a name table owned by the compiled program,
a small pointer to a shared name record), the concrete layout of
=peg_span=, and the field order of the struct.  What is *not* free: equal
names must compare equal, a tag must stay valid for as long as any node
carrying it is alive, and the tag must print verbatim.

** Why =prev= is load-bearing
:PROPERTIES:
:ID:       term-prev
:END:

Two independent pieces of the design need O(1) splice, and both are
served by the same field:

1. *Building a value during parsing.*  The value of a sequence is the
   concatenation of the value lists of its parts, and the value of a
   repetition is the concatenation of its iterations.  With an owned
   forward link, concatenation is: find the tail of the left chain, point
   it at the head of the right chain, fix up the back-link.  With a
   singly linked list every concatenation walks to the tail, which turns
   the hot path quadratic in the number of parts.  =prev= makes the tail
   reachable in O(1).
2. *Editing a result in place.*  D9 names this explicitly: =pegvm= edits
   terms, and "a term's identity must survive an edit that does not touch
   its span" (§5.2).  An edit that inserts or removes a sibling must
   splice it in without rebuilding the chain, or the identity of every
   node after the edit point changes and the incremental claim collapses.

A singly linked list would make the term a write-once AST.  =prev= is
what makes it an editable result.

** What each arrow mode produces
:PROPERTIES:
:ID:       term-arrows
:END:

D2 fixes the mapping.  In the vocabulary of this document:

| Arrow | Value list produced | Nodes allocated |
|-------+---------------------+-----------------|
| =<=   | none — the expression contributes nothing to any enclosing list | none |
| =<-=  | a *flat* list: text nodes only, every =sub == NULL= | one per text piece |
| =<--= | one *structured* node: =tag= is the rule's name, =sub= is the list of its body's values | one per rule application |

- *<= produces no node at all.*  D9's phrase "=<= produces neither; only
  =span= is populated" means the memo *entry* keeps ={rule, id, pos,
  len}=, which is exactly D2's "what is stored per memo entry" column —
  not that a node exists with only a span filled in.  This is the reading
  that makes D2's "a memo hit allocates nothing at all" true, and it is
  *this document's decision* as a reading of D9.
- *<- produces text.*  A text node stores no bytes: its value is
  =(subject, span)=, read on demand.  Nothing is copied, which is what
  keeps the mode cheap on a device and what makes it correct across an
  edit, since a shift moves the span and the bytes follow.
- *<-- produces structure.*  A ~<--~ body may contain ~<=~ parts (they
  vanish from the value list), ~<-~ parts (their flat lists splice
  directly into =sub=), and ~<--~ references (each becomes one child
  node).  This is why ~num <-- digit+~ prints as ~(num "42")~ while
  ~expr <-- term ('+' term)*~ prints as ~(expr (term ...) ...)~.

*Consequence for the printer and for checkers:* the distinction between
the two list shapes is the distinction between "this is text" and "this
is structure", and §7 turns it into an invariant.

** Value lists are ordered concatenations

Formally, every expression has a *value list* — a chain of nodes,
possibly empty:

#+begin_example
value(<= e)        = empty
value(a b)         = value(a) ++ value(b)          (O(1) splice)
value(a / b)       = value(the alternative that matched)
value(a*)          = value(a₁) ++ value(a₂) ++ ... (one term per iteration)
value(terminal)    = [ one text node spanning what it consumed ]
value(rule R)      = per R's arrow: empty (<=), R's flat list (<-),
                     or [ one node tagged R with sub = value(R's body) ]
#+end_example

This is *this document's decision* where PLAN.org leaves granularity
open: one text node per matched terminal.  Its consequences are the ones
that are observable — the printed form (§6) and the cost — and those are
pinned; an implementation that produces one text node per *run* of
adjacent terminals is observably identical in print and cheaper, so it is
allowed (§8).  What is not free: the pieces tile the match in order,
with no gaps and no overlaps among positive-width pieces.

* Spans
:PROPERTIES:
:ID:       term-spans
:END:

** The byte-range convention
:PROPERTIES:
:ID:       term-span-convention
:END:

A span is a half-open byte range =[lo, hi)= of the subject, with
=0 <= lo <= hi=.  Half-open is not a stylistic choice: the memo table's
interval tree is half-open throughout (touching intervals do not overlap),
and a term that used closed ranges would disagree with the structure that
keys it by one byte at every boundary.

- =hi == lo= is legal and means "matched, consumed nothing" (an empty
  literal, an optional that did not match, a rule whose body is ~<=~).
- Offsets are bytes, never characters.  The subject is uninterpreted
  bytes; nothing in this layer knows about text encodings.
- The span of a node is the *matched* extent.  The memo entry's interval
  covers the *examined* extent, which for a PEG is ≥ matched (memo.h).
  The two are different quantities and must not be conflated: the node's
  span is what the printer quotes; the entry's interval is what an edit
  invalidates.

*The memo key.*  A memo lookup is by =(rule id, position)=.  For a
structured node both components are recoverable from the node itself:
=tag= names the rule and =span.lo= is the position.  That is what makes
a term self-describing, and it is the property =pegvm= leans on when it
answers ~captures <start> <end>~ without consulting the bytecode.  For
~<=~ and ~<-~ the identity lives only in the bytecode, which is the price
of D2's cheap modes.

** The span base
:PROPERTIES:
:ID:       term-span-base
:END:

*Requirement.*  A node's =span= is relative to the base position of the
*container* that owns the list the node belongs to.  There are exactly
two bases:

| Container | Base | So a stored span reads as |
|-----------+------+---------------------------|
| a live parse value (a VM stack value, an API handle, a ~captures~ reply) | 0 | an absolute subject offset |
| a memo entry (the table owns the list) | the entry's position | an offset from the entry |

Every read of a span goes through a container-aware accessor; the field
is not to be read directly outside the term module.

*Why.*  This is the existing relocatable-capture scheme (memo.h)
generalized from one capture to a whole list, and it is what makes
incremental reparsing work: a lazy shift moves the entry's position in
O(1) and every span inside it — however many — follows for free.  If
spans were absolute and stored per node, a shift would be O(nodes) per
edit and the incremental claim (D10, §5.2) would be false.

*Consequence.*  Moving a list between containers requires *rebasing*, and
there are exactly two places in the system where that may happen: when a
live value is handed to the memo table on insertion, and when an entry is
materialized for reading.  Both are the memo module's business, not the
term module's, and both are one subtraction.

** Containment and ordering
:PROPERTIES:
:ID:       term-containment
:END:

The invariant between a node and its children, checked over the whole
=sub= tree:

1. *Containment.*  For every node =n= and every node =c= reachable from
   =n->sub= (through the sibling chain, then recursively through =sub=):
   =n.span.lo <= c.span.lo= and =c.span.hi <= n.span.hi=.
2. *Order.*  Within one sibling chain, spans are non-decreasing in =lo=,
   and consecutive *positive-width* siblings do not overlap:
   =b.span.lo >= a.span.hi= for a before b whenever =a.span.lo < a.span.hi=.
   Zero-width siblings may sit anywhere in the order, including at the
   same position as their neighbour.
3. *No tiling requirement.*  Children need not cover the parent.  Gaps
   are expected and come from two sources: ~<=~ sub-expressions (which
   produce no node at all) and predicates (=&p=, =!p=), which consume
   nothing and therefore contribute nothing.  An implementation that
   asserts tiling will reject correct grammars.

*Sibling chains are the only place order is defined.*  Nothing in this
specification orders a node against its cousins, and a consumer must not
assume it.

* Ownership and reference counting
:PROPERTIES:
:ID:       term-ownership
:END:

This section is the one place the rules live; PLAN.org §5.2 asks for it
"with the same rigour as the =vm.c= capture-ownership comment".  A caller
that has not read it will leak or double-free.

** The three ways a node is reached
:PROPERTIES:
:ID:       term-reach
:END:

| reachable through | owned by | owned? |
|-------------------+----------+--------|
| =next= (forward in the sibling chain) | the previous node | *owned* — a node holds one reference to its successor |
| =prev= (backward in the sibling chain) | nobody | *weak* — never counted, never dereferenced during destruction |
| =sub= (the child list) | the parent | *owned* — the parent holds one reference to the head of the chain |

The consequence is the rule everything else follows from: *a sibling
chain is owned as a unit, through its head.*  A chain head is the node
with =prev == NULL=; only a head may be referenced from outside, because
only a head can be.  A pointer to an interior node is a borrowed view,
not an ownership.

** What =ref= and =unref= do
:PROPERTIES:
:ID:       term-ref
:END:

#+begin_c
/* Add one owner.  Precondition: n->prev == NULL (n is a chain head). */
void peg_node_ref(peg_node *n);

/* Drop one owner; destroy n when the count reaches zero. */
void peg_node_unref(peg_node *n);
#+end_c

- =ref= adds one to =n->ref= and touches nothing else.  It does not walk
  the chain, does not touch =sub=, and does not touch any sibling.
- =unref= subtracts one.  While the count stays above zero it does
  nothing else.  At zero, destruction runs (below), which is the *only*
  place a node's links are followed.
- Both are defined only for chain heads.  Referencing an interior node is
  a programming error: its lifetime is already owned by its predecessor,
  so the reference does not protect it as its holder expects.  A checked
  build asserts =n->prev == NULL=.
- A borrowed view confers nothing.  A consumer that receives nodes it did
  not create — a =captures= reply, a memo hit — must not ref, unref,
  mutate, or free them, and must not retain them past the edit that
  invalidates the entry they belong to.  This is the existing memo-table
  contract (memo.h) restated; the term layer does not soften it.

** A node still linked when its last reference goes away
:PROPERTIES:
:ID:       term-linked-zero
:END:

The question an implementer must not have to guess at.  Two cases, and
the first is impossible by construction:

- *Interior node.*  Cannot reach zero.  Its predecessor holds a reference
  to it, so its count is at least one.  Invariant: =ref == 0 ⟹ prev ==
  NULL=.
- *Chain head.*  It reaches zero, and the head is the only node that can.
  Destruction severs the back-link (=next->prev = NULL=) and drops the
  reference the node holds on its =next=.  Two outcomes:
  - if the successor had no other owner, it dies too, and the whole
    remainder of the chain is released — an ordinary consequence of each
    node owning its successor;
  - if the successor *was* referenced from elsewhere (it was borrowed by
    a container), it survives with its count reduced by one, and it is
    now a well-formed chain head: =prev == NULL=, still linked to what
    follows.

*The invariant no implementation may break:* no live node ever has a
dangling =prev= or =next=.  Destruction severs both directions before
freeing, so a node is only freed once nothing reachable points at it.
The =prev= field being weak does not weaken this — it strengthens the
requirement that destruction clears it, because the back-link is not
protected by a count.

** The two-counters hazard (R6)
:PROPERTIES:
:ID:       term-r6
:END:

*The hazard.*  The memo table already reference-counts its captures
(=memo_capture.refs=, memo.h) and it owns them; the term layer
reference-counts nodes; and D9's freeze item 3 makes the node *the
capture payload*.  Two reference-counting schemes meeting at one object
is R6, rated high severity, and it has four distinct failure modes:

1. *Double free* — both schemes reach zero and both run a destructor.
2. *Premature free* — one scheme frees while the other still holds a
   live pointer; a use-after-free that ASan will find and a device will
   not.
3. *Leak* — ownership is split between the two counters, neither reaches
   zero, and the node outlives every parse.
4. *Silent mispositioning* — a node written while entry-relative and read
   as if absolute yields positions that are wrong by the entry's offset
   *and keep being wrong after every subsequent edit*.  S7 names this as
   the real cost behind D9: not the struct change, the lifetime graph.

*What the specification requires to avoid it.*

1. *Exactly one count per node: =ref=.*  There is no second counter, on
   the node or beside it.  Any existing per-capture count is subsumed.
2. *Every owner goes through the same two functions.*  A memo entry owns
   nodes by calling =peg_node_ref= on a chain head and =peg_node_unref=
   when it evicts — it is an owner like any other, not a parallel system.
3. *One free path.*  Only the term module destroys nodes.  The memo table
   never calls =free= on a node, and never allocates one except through
   the term constructors.
4. *Two rebase points, named in §3.2, and no others.*  A node reachable
   from two containers with two bases is the mispositioning bug; the
   ownership rules above are what make it impossible, since an
   exclusively-owned list has exactly one container.
5. *Borrowing is not ownership.*  A memo hit returns a borrowed view
   (§4.2), which is why a caller cannot hold it across an edit and cannot
   create a second owner that the table does not know about.
6. *Land it behind a sanitizer.*  R6's mitigation, and the project's
   standing rule: ASan/UBSan clean with zero leaks on every suite before
   anything depends on terms.  A leak test that parses, edits, and
   discards is part of the term suite, not an afterthought.

* Freeing and traversal must be iterative
:PROPERTIES:
:ID:       term-iterative
:END:

*Requirement.*  Destroying a list, and traversing one (including the
printer, §6), must use bounded call stack.  Recursive destruction or
recursive printing is a defect, not a style choice.

*Why.*  D8 puts the floor at Cortex-M/ESP32 with ≥64 KB RAM, where the
stack is a few kilobytes and a fault is silent corruption rather than a
clean crash.  The depth that breaks recursion is not exotic: a sibling
chain is as long as the input produces, so a deep chain must not consume
stack proportional to its length — and S5 records that teardown and
traversal currently recurse to input depth.  R13's mitigation (a ≥10k
nesting stress test) is the corresponding test and is required here too.

** The destruction algorithm
:PROPERTIES:
:ID:       term-destroy
:END:

The property that makes an allocation-free, O(1)-auxiliary, non-recursive
destructor possible is that a chain is entered only at its head, and a
head's =prev= is unused.  Reuse it as the link of an explicit pending
stack:

#+begin_c
/*
 * Destroy 'head' -- whose ref has just reached zero -- and everything it
 * owns.  O(1) auxiliary space, no recursion: the pending set of child
 * lists is threaded through the 'prev' field of the nodes waiting to be
 * destroyed, which is legal because a chain head's prev is otherwise
 * unused and every node on that stack is still alive when it is read.
 *
 * The loop is also where §4.3's second outcome happens: a successor that
 * is owned from elsewhere has ref > 1, survives, and becomes a well
 * formed head (prev == NULL).
 */
static void peg_node_destroy(peg_node *head)
{
	peg_node *n = head, *pending = NULL;

	while (n != NULL) {
		peg_node *next = n->next;
		bool keep_next = false;

		if (next != NULL) {
			next->prev = NULL;          /* sever first: no live
							 node may point at
							 what we are about to
							 free                    */
			keep_next = (--next->ref != 0);
		}
		if (n->sub != NULL) {
			n->sub->prev = pending;     /* push the child list */
			pending = n->sub;
		}
		peg_free(n);

		if (keep_next) {
			n = next;                   /* the chain continues */
		} else {
			n = pending;
			if (pending != NULL)
				pending = pending->prev;   /* pop */
		}
	}
}
#+end_c

=peg_free= is the =peg_alloc= vtable's free (freeze item 2); the term
module never calls =free= directly, and on a device the whole chain may
come from a bump arena that is reset in one shot instead.

Note what the loop does *not* do: it never reads a node's =prev= for
anything but the pending stack, it never walks a chain twice to find a
tail, and it holds no more auxiliary state than a chain of nesting depth.

* The s-expression printer
:PROPERTIES:
:ID:       term-printer
:END:

D9: "Debug printout is an s-expression ... and that same printer is the
wire format for =pegvm= replies (D10)."  There is one printer, its output
is canonical, and =docs/protocol.org= depends on both facts.

** The printed forms
:PROPERTIES:
:ID:       term-print-forms
:END:

| thing printed | form |
|---------------+------|
| a text node | one quoted string of the subject bytes over its span, escaped per §6.2 |
| a structured node | =tag= in parentheses, then the value list: ~(tag ...)~, or ~(tag)~ when the list is empty |
| a value list whose elements are *all* text nodes | one quoted string: the bytes of all the pieces concatenated |
| any other list | its elements, each printed as above, separated by exactly one space |
| the empty list | ~()~ |

The "all text nodes" case is what makes the two modes read differently,
and it is the reason the printer needs no special case per arrow:

#+begin_example
expr <- term ('+' term)*     ->  "1+2+3"            (flat list, one string)
expr <-- term ('+' term)*    ->  (expr (term "1") ...)   (structure)
#+end_example

It is *this document's decision* and it is not arbitrary: an all-text
list carries no structure, so printing it as a sequence of quoted
fragments would expose a granularity (§2.4) that the specification
otherwise leaves free and that a reader could not act on.  Concatenating
it makes the printed form a lossless, granularity-independent
description of the value.

** Escaping, byte for byte
:PROPERTIES:
:ID:       term-escaping
:END:

Inside a quoted string, each byte of the piece is written as:

| byte | written as |
|------+------------|
| =0x22=, the double quote | =\"= |
| =0x5C=, the backslash | =\\= |
| =0x0A= LF | =\n= |
| =0x0D= CR | =\r= |
| =0x09= TAB | =\t= |
| any other =0x00–0x1F=, and =0x7F= | =\xHH= — exactly two *lowercase* hex digits |
| =0x20–0x7E= except the two above | the byte itself |
| =0x80–0xFF= | the byte itself |

Bytes in =0x80–0xFF= pass through unescaped: the printer is
byte-transparent and does not validate or transcode anything, so a UTF-8
subject prints as UTF-8.

*Three properties that follow, all of them load-bearing.*

1. *Canonical.*  A byte string has exactly one printed form.  There is no
   choice between =\x0a= and =\n=, or between =\x0A= and =\x0a=: LF is
   always =\n= and hex is always lowercase.  Two terms that differ print
   differently, and two printed forms that differ denote different terms.
2. *One line.*  No escape ever emits a raw =0x0A= or =0x0D=, so a printed
   term never contains a line break.  This is *why* the =pegvm= protocol
   can be line-oriented (docs/protocol.org §3.2) and why a client needs
   no parenthesis balancing to find the end of a reply.
3. *Round-trippable.*  The reader (=src/read/sexpr_reader.c=) accepts
   exactly this escape set — =\"=, =\\=, =\n=, =\r=, =\t=, =\xHH= (either
   case) — plus whitespace and =;=-to-end-of-line comments between atoms,
   and rejects everything else.  =read(print(t)) == t= for every term =t=.
   Note the consequence for hand-written corpus files: they must use these
   escapes; a C escape the printer never emits (==\0=, ==\a=, ==\uXXXX=,
   or an uppercase hex choice where the printer would use a named one) is
   not part of the language.

A parenthesis inside a string is not escaped: the quotes delimit it,
so no ambiguity exists.

** Worked examples
:PROPERTIES:
:ID:       term-print-examples
:END:

#+begin_example
Subject "1+2+3", rule  expr <- term ('+' term)*
  value list   [ "1" "+" "2" "+" "3" ]      (all text)
  printed      "1+2+3"

Subject "1+2+3", rule  expr <-- term ('+' term)*
  value        (expr), sub = [ (term) with sub ["1"] ... ]
  printed      (expr (term "1") (term "2") (term "3"))

A JSON fragment under  (value (string ...) (number ...)):
  printed      (pair (key "a") (val "1"))

An empty value list (a <- rule whose body matched nothing, or a <=
result):        ()
A structured node with an empty value list:  (novalue)

Bytes  'a' '"' 'b' '\' 'c' LF TAB 0x01
  printed      "a\"b\\c\n\t\x01"

A structured node with a flat run in the middle of its children:
  printed      (x "a" (y "b") "c")
#+end_example

* The flat/structured invariant
:PROPERTIES:
:ID:       term-invariant
:END:

D2 and D9 make the ~<-~/~<--~ distinction structural, so a checker can
verify it over a finished term without knowing the grammar.  Three
statements, all mechanical:

1. *Flatness of ~<-~.*  Every node reachable from a ~<-~ rule's value list
   has =sub == NULL=.  A ~sub != NULL~ node anywhere under a ~<-~ result
   means a ~<--~ reference reached a ~<-~ body, which the grammar must
   reject at compile time (docs/grammar.org) — the checker catches the
   case where it did not.
2. *Text nodes are leaves and are anonymous.*  =tag == NULL= ⟹ =sub ==
   NULL=; =sub == NULL= does not imply =tag == NULL= (=a ~<--~ node with
   an empty value list is legal, and prints as ~(tag)~).
3. *Containment and order (§3.3) hold everywhere,* with no exception for
   boundary cases: a zero-width node is inside its parent's span like any
   other.

*What the checker is.*  A debug-build walk of a result term, iterative
(§5), run in tests and behind an assertion; it takes the compiled
program's map from rule name to arrow so that statement 1 can be
evaluated.  It is a test-time obligation, not a runtime cost on a device.

*The one thing the checker cannot see* is whether a ~<-~ value's text is
what the grammar intended to capture.  That is the differential suite's
job: incremental reparse must produce byte-identical printed terms to a
full reparse (test_peg.c's discipline, extended — PLAN.org §3 notes the
existing incremental differentials never compare captures).

** Free choices (the collected implementer's-discretion list)
:PROPERTIES:
:ID:       term-discretion
:END:

Each of these must be documented in =include/peg/peg_term.h=, because a
caller that cannot see the header cannot see the choice:

1. The representation behind =peg_tag= and the layout of =peg_span=,
   subject to §2.1's requirements.
2. The concrete granularity of text pieces (§2.4), subject to the
   printed form of §6.1 and to the tiling requirement.  One text node per
   matched terminal is the reference behaviour.
3. The storage for the printer's output (caller-supplied buffer, growable
   arena, or an allocation hook), since the device build must not be
   forced to allocate.
4. Whether a device build resets a bump arena instead of walking chains
   to free them, provided the arena cannot be reset while a node is still
   owned by an entry or a live value.

** Open questions from PLAN.org that touch this document
:PROPERTIES:
:ID:       term-question
:END:

None of these is resolved here; each is recorded with its consequence so
that a reader can see what changes when it is answered.

- *Q5 — does =:name= control memoization or only name a value?*  If it
  controls memoization, fewer values exist and fewer nodes are built, but
  the node representation is unaffected.  It does change what a ~captures~
  reply can contain (docs/protocol.org).
- *Q6 — the memoization default per arrow, and tree-memoization syntax.*
  This document assumes every rule is memoized with the payload D2's table
  gives, and assumes nothing about tree memoization.  If tree memoization
  can re-group a result's children (the existing dummy-capture machinery
  does exactly that, and S6(b) records that it makes capture *shape*
  differ between modes), then a printed term can differ between a full and
  an incremental parse without either being wrong — which would break the
  differential test above.  *This needs an answer before the printer is
  frozen.*
- *Q7 — how the grammar's own incremental reparse is keyed.*  Relevant
  here only through §3.2: if a node can be owned by two containers whose
  bases differ, the rebase rule is not sufficient.
